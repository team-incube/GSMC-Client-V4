# GSMC Client V4

Frontend monorepo for the GSM certification service (GSMC). These instructions apply to every coding agent (Claude Code, Codex, Gemini CLI, Cursor, Copilot, ...).

## Language

- Write all user-facing output in **Korean**: responses, commit messages, issue and PR titles and bodies, code review results.
- Agent instruction documents (`AGENTS.md`, `CLAUDE.md`, `.claude/**`) are written in English. Keep them in English when editing.

## Structure

Turborepo + npm workspaces.

| Path | Role |
|---|---|
| `apps/client` | Student-facing Next.js app (port 3000) |
| `apps/admin` | Admin Next.js app (port 3001) |
| `packages/ui` (`@repo/ui`) | Shared components, design tokens (`src/styles/theme.css`), theme |
| `packages/lib` (`@repo/lib`) | `apiClient` (axios), `queryClient` |
| `packages/typescript-config` | Shared tsconfig |

Stack: Next.js 16 (App Router), React 19, Tailwind CSS v4, TanStack Query v5, axios, sonner.

## Commands

```bash
npm run dev      # all dev servers
npm run build
npm run lint
npx tsc --noEmit -p apps/client   # type check (per app)
```

Before finishing a change, run lint and the type check for every app you touched. If `packages/*` changed, type check both apps.

## Must follow

- **Next.js 16 differs from your training data.** Before writing Next.js code, read the relevant guide in `node_modules/next/dist/docs/`.
- App source follows FSD: `app → views → features`.
- Use only `theme.css` color tokens (`text-strong`, `bg-surface`, `border-line`, ...). Never hardcode hex colors.
- Before creating a component, check whether `@repo/ui` already has it. Code used by both apps goes to `packages/`.
- Apps never import from each other. Shared code is imported only via `@repo/*`.
- Never read or print `.env*` files (except `.env.example`), and never write secrets into source.

## Git

- **Issue first.** Before writing code for a task, confirm its issue number. If there is none, offer to create one and wait — do not start implementing.
- Branch `<type>/<description>` from `develop` (e.g. `feat/faq-accordion`), PR into `develop` tagging the issue (`#20`). Never commit or push directly to `main` or `develop`, and never force push.
- Commit `type(scope): 한국어 설명`, e.g. `feat(client): FAQ 검색 기능 구현`.
- Issues and PRs use the templates in `.github/`. Every issue needs a Type and a Priority label; every PR needs a Type label.
- The only PR without an issue is the `develop` → `main` release PR (`merge to main`, label `🪽 Type: Release`).

## Skills

Shared workflows live as skills: `.claude/skills/` for Claude Code, mirrored to `.agents/skills/` for Codex and other agents that read that directory.

| When | Skill |
|---|---|
| Create an issue | `issue` |
| Commit | `commit` |
| Open a PR | `pr` |
| Requirements are vague or a feature has several design decisions | `planning` → spec in `docs/specs/` |
| Any bug, error, or unexpected behavior | `systematic-debugging` |
| Review a diff for defects | `review-diff` |
| Add a page | `new-page` |
| Add a shared UI component | `new-ui-component` |

**Edit skills and agents only under `.claude/`.** `.agents/skills/` and `.codex/agents/` are generated by `node .claude/scripts/sync-agents.mjs`; changes made there are overwritten.
